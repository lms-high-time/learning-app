# Как писать тесты

Правила для тестов приложения — и для людей, и для агентов. Цель одна: каждая
ветка кода проверена, и проверена один раз. Лишний интеграционный тест не
бесплатен: он заводит данные в базе, замедляет каждый PR и требует правки при
каждом изменении поведения.

`Why:` аудит тестов 9 октября 2026 (learning-services#532) нашёл около пятой
части интеграционных тестов лишними. Причины повторялись во всех областях:
тест заводили под ишью, а не под слой кода, поэтому одну ветку проверяли
сервис, метод API и соседний файл; каждое `assert` становилось отдельным
тестом с полной подготовкой данных; чистую логику гоняли через базу.

## 1. Ветка проверяется один раз, на нижнем уровне

Чистая функция — юнит-тестом. Сервис, которому нужна база, — интеграционным.
Метод API проверяет только проводку: что он зовёт сервис и отдаёт его ответ.
Перевод `Отказ` в код контракта общий — декоратор `контракт` в
`lms_frappe_app/api/__init__.py`, — поэтому у метода на него один случай, а не
по случаю на каждый код отказа сервиса. Отказы, которые порождает сам метод,
проверяются в тесте метода. Ошибки прав декоратор не перехватывает, агент
видит 403, — это проверки безопасности, раздел «Что не удаляется».

`Why:` ветка, проверенная на трёх уровнях, при изменении поведения правится в
трёх местах, и пропуск одного из них даёт красный тест на ровном месте.
Например, `course_not_found` проверялся семью тестами в шести файлах.

**How to apply:** перед новым тестом найти, где ветка уже проверена: грепнуть
по имени функции, коду отказа и тексту ошибки в `test_*.py`. Нашлось на нижнем
уровне — новый тест не нужен; на верхнем — перенести проверку вниз, а наверху
оставить проводку.

## 2. Одно действие — один тест

Одно действие с несколькими следствиями проверяется одним тестом с несколькими
`assert`. Матрица «роль × действие», набор входов одного правила — таблицей
через `subTest`, а не отдельным тестом на строку.

`Why:` у интеграционного теста дорога подготовка данных, а не сама проверка:
матрица прав, разрезанная на девять тестов, девять раз заводит пользователей
и курс.

**How to apply:** пример таблицы —
`lms_frappe_app/api/test_notes_reports_guard.py`: пути записи собраны в
словарь, каждый проверяется в своём `subTest`, и упавшая строка видна по
имени.

## 3. Без базы — без интеграционного класса

Тесты чистых функций и мета-тесты (схема, порядок патчей, состав хуков) не
наследуют `IntegrationTestCase`. Новые пишутся на `frappe.tests.UnitTestCase`.

`Why:` `IntegrationTestCase` относит тест к интеграционному прогону: перед ним
`run-tests` зовёт `before_tests`, а класс в `setUpClass` готовит сайт и
тестовые записи доктайпа и коммитит их. Откат транзакции один — после класса.
Тесту без базы эта подготовка не нужна. `UnitTestCase` попадает в категорию
`unit`: она идёт первой, до `before_tests`, и запускается отдельно
(`--test-category unit`). Голый `unittest.TestCase` идёт в категорию «без
категории», последним, и `--test-category unit` его не видит. Работающие
тесты на нём переписывать ради этого не нужно.

**How to apply:** тест без интеграционного класса **не пишет в базу**:
отката у него нет, и записанное закоммитит первый же интеграционный класс.
Логику, которую не проверить без базы, потому что она внутри функции с
запросами, выносить в чистую функцию и проверять юнитом. Примеры без базы —
`lms_frappe_app/agent_learning/artifacts/test_tables.py`,
`lms_frappe_app/agent_learning/releases/test_schema.py`.

## 4. Данные — когда нужны

Данные, которые нужны немногим тестам класса, не создаются в общем `setUp`.

`Why:` `setUp` выполняется перед каждым тестом класса, и курс, нужный двум
тестам из двадцати, заводится двадцать раз. Откатываются эти данные только
после класса, так что они ещё и копятся в его транзакции.

**How to apply:**
- данные, которые тесты класса только читают, — в `setUpClass`: создаются один
  раз и откатываются вместе с классом;
- данные, которые тест меняет, — в самом тесте, чтобы соседние тесты не
  зависели от порядка;
- данные немногих тестов — хелпером, который создаёт запись при первом
  обращении и дальше отдаёт её же.

## 5. Тест одноразового патча уходит вместе с патчем

Когда удаляется патч — правило в [README](README.md#одноразовые-патчи),
«Одноразовые патчи». Пока патч стоит в `patches.txt`, его тест при чистке
дублей не трогают.

## Что не удаляется

При чистке дублей эти тесты не удаляются. Их можно только объединять в
таблицу, сохраняя каждый случай:

- **ворота** — тест, который обходит все методы, схемы или доктайпы и падает на
  новом неучтённом: `lms_frappe_app/api/test_query_budget.py`,
  `lms_frappe_app/api/test_contract.py`,
  `lms_frappe_app/tests/test_unsanitized_fields.py`,
  `lms_frappe_app/api/test_no_leak.py`;
- **безопасность** — тест, что роль или пользователь не может прочитать или
  изменить чужое: ошибка прав, отказ в доступе к чужим данным. Такая проверка
  нужна один раз на каждом пути, где своя проверка доступа; повтор того же
  отказа в методе, который проверку не делает, а наследует от сервиса, — дубль;
- **гонки** — тест на одновременные вызовы;
- **регрессия** — тест, в docstring которого стоит номер ишью с ошибкой: эта
  ошибка уже случалась. Номер ишью в docstring модуля регрессией тест не
  делает — так помечают задачу, под которую завели файл.

`Why:` они проверяют не ветку кода, а обещание — бюджет запросов, контракт,
закрытый доступ, повторившуюся ошибку. Дубль у такого теста бывает только
мнимый.
